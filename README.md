# 海底长期观测阵列 · 翻转通道联合归因

回收阵列后，维护工程师录入按编号排列的采集通道与多轮校验记录（每条含**非空通道集合**、
**预期二值**、**实测二值**），应用在浏览器本机联合求解发生翻转（故障）的通道集合，
并展示故障通道、每条记录的推导奇偶与结论。全部计算在本机完成，不向外部发送数据。

## 归因模型

对每条记录，当且仅当其通道集合中故障通道数为**奇数**时，实测相对预期翻转：

```
⊕_{c ∈ 集合} x_c = 预期 XOR 实测        (x_c ∈ {0,1})
```

所有记录必须由**同一个**故障集合同时满足（GF(2) 线性方程组），严禁按单条记录独立归因
而得到彼此冲突的维修名单。

求解流程（`src/attribution.ts`）：

1. 高斯–若尔当消元（RREF，bitset 实现）；出现 `0 = 1` 行即**无联合解**。
2. 解为仿射空间 `x = base ⊕ ⊕ 自由变量列`；以 Gray 码枚举全部解（相邻解一次异或更新），
   统计并保留 popcount（故障数）最小者。
3. 等优方案间按**通道编号序列字典序**（故障编号升序后逐元素比较）取最小者为主方案，
   次小者为第二份见证，并给出两者的首个分歧通道。
4. 30 通道上限使枚举规模至多 2^24（Gray 码，秒级完成）。

## 页面行为

- 通道 8–30 个、校验记录 6–24 条；提交前完整校验（非空、正整数、无重复、编号须在通道表内）。
- **修改任何草稿立即撤销旧诊断**，页面不再保留与当前输入不符的旧名单。
- 有解：展示故障通道（故障数最少、字典序最小）、第二份见证与首个分歧通道（最小解唯一时省略）、
  以及每条记录的集合内故障通道数、推导奇偶、要求奇偶、是否解释差异。
- 无解：明确显示「无联合归因结论」且不保留旧名单。

## 本地开发

```bash
npm ci
npm test        # vitest 单元测试
npm run dev     # 开发服务器（含 /healthz）
npm run build   # 类型检查 + 生产构建
npm run smoke   # 归因模块冒烟（退出码报告）
```

## Docker / Compose

站点端口通过 `WEB_PORT` 配置（默认 8080，仅绑定 127.0.0.1）：

```bash
WEB_PORT=9090 docker compose up web      # 仅启动站点
docker compose up                        # 站点 + verify 一次性校验
```

- `web`：nginx 托管静态站点，`HEALTHCHECK` 轮询 `/healthz`。
- `verify`：一次性服务，`depends_on: service_healthy`，待站点健康后依次执行
  **代码测试 → 生产构建 → 归因模块冒烟**，以退出码报告（非零即失败）。
